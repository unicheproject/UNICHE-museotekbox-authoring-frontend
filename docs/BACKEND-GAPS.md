# Τι λείπει από το backend για να ολοκληρωθούν τα CRUD

Σύντομη λίστα με τα σημεία όπου το frontend είναι **έτοιμο και σταματά** επειδή δεν υπάρχει
endpoint. Το αναλυτικό πλάνο ανά οντότητα είναι στο `docs/crud-plan.md` (Μέρος Β) — εδώ μένουν
μόνο όσα μπλοκάρουν κώδικα που έχει ήδη γραφτεί και μπει στο repo.

Ορολογία κατά `CLAUDE.md`: το UI λέει **Experience**, το API λέει **Project**.

## 1. Boxes — δεν υπάρχει τίποτα

Δεν υπάρχει έννοια box στο API. Μπλοκάρει δύο πράγματα:

- Την ενότητα **Boxes** στο μενού (`/boxes`, `src/views/BoxesSection.vue`), που τώρα δείχνει
  «Coming soon».
- Το «σε ποια box είναι ανατεθειμένο» στη σελίδα του experience. Το UI δεν έχει καν πού να
  ρωτήσει, οπότε η ενότητα δεν μπήκε καθόλου αντί να μπει άδεια.

Χρειάζονται: λίστα boxes ανά οργανισμό, τα experiences που είναι ανατεθειμένα σε ένα box, και η
**αντίστροφη αναζήτηση** — για ένα project id, σε ποια boxes εμφανίζεται.

## 2. Members — δεν υπάρχει τίποτα

Το `GET /me/authorization` λέει τι μπορεί να κάνει *ο συνδεδεμένος χρήστης*, αλλά δεν υπάρχει
τρόπος να δεις **ποιοι άλλοι** έχουν πρόσβαση σε έναν οργανισμό. Μπλοκάρει την ενότητα
**Members** (`/members`, `src/views/MembersSection.vue`).

Χρειάζονται: λίστα μελών ενός οργανισμού με τον ρόλο του καθενός, αλλαγή ρόλου, αφαίρεση μέλους.

## 3. Library — δεν υπάρχει τίποτα

Μπλοκάρει την ενότητα **Library** (`/library`, `src/views/LibrarySection.vue`). Χρειάζονται
λίστα, ανέβασμα και διαγραφή για τα κοινά αρχεία/περιεχόμενο ενός οργανισμού.

## 4. Λίστα οργανισμών του χρήστη

Υπάρχει `GET /organisations/{orgId}` για **έναν** οργανισμό, αλλά όχι λίστα. Έτσι το frontend
μαθαίνει για οργανισμούς **μόνο** μέσα από το `/me/authorization` και μετά ρωτά έναν-έναν με
το `src/lib/useOrgNames.ts`.

Πού πονάει: στη σελίδα **διαγραμμένων experiences**
(`src/views/DeletedExperiences.vue`). Το `GET /organisations/{orgId}/projects/deleted` είναι
platform-admin-only, αλλά ένας platform admin μπορεί να έχει άδειο `managedOrganisations` — οπότε
του προσφέρουμε επιλογή οργανισμού **μόνο** από όσους τυχαίνει να εμφανίζονται στο δικό του
authorization context. Πρακτικά ένας admin δεν μπορεί να δει τα διαγραμμένα ενός οργανισμού που
δεν διαχειρίζεται ο ίδιος.

Χρειάζεται: `GET /organisations` (όσοι είναι ορατοί στον χρήστη, όλοι για platform admin).

## 5. Server-side αναζήτηση, ταξινόμηση, σελιδοποίηση

Τα `GET /organisations/{orgId}/projects` και `.../projects/deleted` επιστρέφουν **σκέτο πίνακα**,
χωρίς `page`, `size`, `sort`, `q`. Άρα αναζήτηση, ταξινόμηση και σελιδοποίηση γίνονται
**client-side** (`src/lib/useDataList.ts`).

Δεν είναι blocker για το v1 — δουλεύει σωστά στον σημερινό όγκο. Γίνεται πρόβλημα όταν ένας
οργανισμός φτάσει μερικές εκατοντάδες experiences: κατεβάζουμε όλα για να δείξουμε 12. Όταν
έρθει η ώρα, το `useDataList` αλλάζει σε server-side παραμέτρους χωρίς να αλλάξουν οι σελίδες.

## 6. Cross-organisation λίστα experiences

Δεν υπάρχει endpoint που να επιστρέφει τα projects **όλων** των οργανισμών του χρήστη. Η σελίδα
Experiences κάνει μία κλήση ανά οργανισμό και τις ενώνει. Λειτουργεί, αλλά ο αριθμός κλήσεων
μεγαλώνει με τους οργανισμούς. Χαμηλή προτεραιότητα.

## 7. Πεδία που θα βοηθούσαν στο `ProjectDto`

Το `ProjectDto` έχει σήμερα `id`, `orgId`, `name`, `slug`, `status`, `toolSlug`. Λείπουν
`createdAt` / `updatedAt`, που θα επέτρεπαν ταξινόμηση «πιο πρόσφατα πρώτα» — το πιο φυσικό
default για λίστα experiences — και «τελευταία αλλαγή» στη σελίδα του experience. Τώρα η
προεπιλεγμένη ταξινόμηση είναι αλφαβητική, επειδή δεν υπάρχει ημερομηνία.

Επίσης το status δεν είναι τεκμηριωμένο enum, οπότε το UI παράγει τις επιλογές του φίλτρου από
τα δεδομένα και τα άγνωστα status παίρνουν ουδέτερο χρώμα (`src/lib/status.ts`).
