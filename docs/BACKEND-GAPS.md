# Τι λείπει από το backend για να ολοκληρωθούν τα CRUD

Σύντομη λίστα με τα σημεία όπου το frontend είναι **έτοιμο και σταματά** επειδή δεν υπάρχει
endpoint ή δεν είναι τεκμηριωμένη μια τιμή. Το αναλυτικό πλάνο ανά οντότητα είναι στο
`docs/crud-plan.md`. Εδώ μένουν μόνο όσα μπλοκάρουν κώδικα που έχει ήδη μπει στο repo.

Ορολογία κατά `CLAUDE.md`: το UI λέει **Experience**, το API λέει **Project**.

## 1. Scan object types — δεν υπάρχει τίποτα, και μολύνει τα scan objects

Ο τύπος υπάρχει στο μοντέλο: κάθε scan object έχει `scanObjectTypeId`. Δεν υπάρχει όμως **κανένα**
endpoint για τους τύπους — ούτε λίστα, ούτε δημιουργία, ούτε μετονομασία, ούτε διαγραφή.

Η συνέπεια δεν είναι μόνο ότι λείπει μια σελίδα. Στη φόρμα δημιουργίας ενός scan object ο χρήστης
πρέπει να διαλέξει τύπο· χωρίς λίστα, το μόνο που μπορεί να του δώσει το UI είναι να **γράψει τον
αριθμό** του τύπου με το χέρι, και το φίλτρο της λίστας δείχνει «Type 3» αντί για όνομα. Είναι το
πιο επείγον από όλα.

Χρειάζονται: λίστα τύπων ανά οργανισμό, δημιουργία, μετονομασία, διαγραφή. Επιπλέον, ο κάθε τύπος
να επιστρέφει **πόσα αντικείμενα τον χρησιμοποιούν** (αλλιώς το UI θα πρέπει να κατεβάσει όλα τα
αντικείμενα για να μετρήσει), και η διαγραφή να απαντά με **διακριτό κωδικό σφάλματος** όταν ο
τύπος είναι σε χρήση, ώστε να βγαίνει σωστή προειδοποίηση αντί για γενικό μήνυμα.

## 2. Scan objects — δουλεύουν, με τρεις ασάφειες

Τα CRUD υπάρχουν και η σχεδίαση με ξεχωριστό endpoint ανά είδος ταιριάζει στη φόρμα που αλλάζει
ανά είδος. Τρία σημεία θέλουν απάντηση:

- **Το `kind` δεν είναι τεκμηριωμένο enum.** Το UI το χρειάζεται για να ξέρει σε ποιο από τα
  τέσσερα PATCH endpoints να στείλει μια επεξεργασία. Το `resolveScanObjectKind` στο
  `src/api/museotekBox.ts` δέχεται ανεκτικά όλες τις πιθανές γραφές, και όταν δεν αναγνωρίσει την
  τιμή **απενεργοποιεί** την επεξεργασία αντί να μαντέψει endpoint. Ζητούμενο: το επίσημο σύνολο
  τιμών.
- **Λύσιμο RFID tag.** Δεν υπάρχει ξεχωριστή ενέργεια· το UI το κάνει με PATCH στο `rfidTag`. Δεν
  είναι τεκμηριωμένο αν το `null` καθαρίζει το πεδίο ή αγνοείται. Γι' αυτόν τον λόγο το UI στέλνει
  **πάντα ολόκληρο** το σύνολο πεδίων, ώστε καμία ερμηνεία να μη σβήσει άλλο πεδίο κατά λάθος.
  Ζητούμενο: επιβεβαίωση ότι το `null` λύνει το tag.
- **Εικόνα και τρισδιάστατο μοντέλο δεν ανεβαίνουν.** Τα `imageUrl` και `modelRef` είναι σκέτα
  κείμενα, οπότε η φόρμα ζητά **αναφορά** και όχι αρχείο. Για πραγματικό ανέβασμα θέλει endpoint
  αρχείων.

Θετικό: το 409 στο δέσιμο tag είναι αρκετό για να πει το UI «αυτό το tag είναι δεμένο σε άλλο
αντικείμενο». Αν υπάρχει και σταθερός `code` στο envelope, το μήνυμα γίνεται ακριβέστερο.

## 3. Boxes — δουλεύουν μισά

Λίστα, δημιουργία, μετονομασία, διαγραφή και η ενδεικτική κατάσταση υπάρχουν. Λείπουν:

- **Ορισμός του experience που τρέχει.** Το `UpdateBoxRequest` δέχεται μόνο `name` και
  `serialNumber`, οπότε το `currentProjectId` είναι μόνο για ανάγνωση.
- **Ανάθεση και αφαίρεση experiences** σε ένα box, και η **αντίστροφη αναζήτηση** «σε ποια boxes
  βρίσκεται αυτό το experience». Γι' αυτό η σελίδα του experience δεν δείχνει boxes.
- **Χρόνος τελευταίας επικοινωνίας.** Υπάρχει `status` αλλά κανένα `lastSeenAt`, οπότε το «πότε το
  είδαμε τελευταία φορά» δεν μπορεί να εμφανιστεί.
- **Το `status` δεν είναι τεκμηριωμένο enum.** Το UI θεωρεί online μόνο την τιμή `ONLINE` και
  οτιδήποτε άλλο μη-online, χωρίς να επινοεί τρίτη κατάσταση.

Η κατάσταση ανανεώνεται με περιοδική κλήση κάθε 10 δευτερόλεπτα, που **παύει όταν η καρτέλα δεν
είναι μπροστά**. Αν προτιμάτε push αντί για polling, πείτε το.

## 4. Χρήστες / Members — δεν υπάρχει τίποτα

Το `GET /me/authorization` λέει τι μπορεί **ο συνδεδεμένος** χρήστης, αλλά δεν υπάρχει τρόπος να
δει κανείς **ποιοι άλλοι** έχουν πρόσβαση. Μπλοκάρει και τις δύο οθόνες, μέλη οργανισμού και μέλη
experience (`/members`, `src/views/MembersSection.vue`).

Χρειάζονται: λίστα μελών οργανισμού και λίστα μελών experience, με όνομα, mail και ρόλο· αλλαγή
ρόλου· αφαίρεση μέλους· και **αναζήτηση χρήστη** για την προσθήκη νέου μέλους.

## 5. Library — δεν υπάρχει τίποτα

Μπλοκάρει την ενότητα Library (`/library`, `src/views/LibrarySection.vue`). Χρειάζονται λίστα,
ανέβασμα και διαγραφή για τα κοινά αρχεία ενός οργανισμού.

## 6. Λίστα οργανισμών

Υπάρχει `GET /organisations/{orgId}` για **έναν** οργανισμό, αλλά όχι λίστα. Το frontend μαθαίνει
για οργανισμούς μόνο μέσα από το `/me/authorization` και μετά ρωτά έναν-έναν
(`src/lib/useOrgNames.ts`, `src/lib/useOrgScope.ts`).

Πού πονάει: στη σελίδα **διαγραμμένων experiences**. Το
`GET /organisations/{orgId}/projects/deleted` είναι platform-admin-only, αλλά ένας platform admin
μπορεί να έχει άδειο `managedOrganisations` — οπότε δεν μπορεί να δει τα διαγραμμένα ενός
οργανισμού που δεν διαχειρίζεται ο ίδιος.

Χρειάζεται: `GET /organisations` (όσοι είναι ορατοί στον χρήστη, όλοι για platform admin).

## 7. Server-side αναζήτηση, ταξινόμηση, σελιδοποίηση

Κανένα endpoint λίστας δεν δέχεται `page`, `size`, `sort` ή `q`. Άρα όλα γίνονται **client-side**
(`src/lib/useDataList.ts`).

Δεν είναι blocker τώρα. Γίνεται πρόβλημα όταν ένας οργανισμός φτάσει εκατοντάδες experiences ή
scan objects: κατεβάζουμε όλα για να δείξουμε δεκαπέντε. Όταν έρθει η ώρα, το `useDataList`
αλλάζει σε server-side παραμέτρους χωρίς να αλλάξουν οι σελίδες.

## 8. Μικρότερα

- Δεν υπάρχει endpoint που να επιστρέφει τα projects **όλων** των οργανισμών του χρήστη· η σελίδα
  Experiences κάνει μία κλήση ανά οργανισμό και τις ενώνει. Χαμηλή προτεραιότητα.
- Το `status` του project επίσης δεν είναι τεκμηριωμένο enum, οπότε το UI παράγει τις επιλογές του
  φίλτρου από τα δεδομένα και τα άγνωστα status παίρνουν ουδέτερο χρώμα (`src/lib/status.ts`).

## Τι καλύφθηκε πρόσφατα

Για ιστορικό: το `ProjectResponse` απέκτησε `createdAt` και `updatedAt`, οπότε η λίστα των
Experiences ταξινομείται πλέον εξ ορισμού «πιο πρόσφατα πρώτα». Το `ErrorEnvelope` απέκτησε
`requestId`. Και το `toolSlug` έφυγε από το `CreateProjectRequest` — το backend το ορίζει μόνο του.
